허용목록은 아직 수정되지 않았다. 조치가 없으면 다음 회차도 같은 지점에서 멈춘다.

원인

클라우드 루틴 실행 환경의 네트워크 egress 허용목록에 arXiv 호스트가 없다.

``` $ python3 0-papers/.radar/fetch.py urllib.error.HTTPError: HTTP Error 403: Forbidden

$ curl http://export.arxiv.org/api/query?... 403 — Host not in allowlist: export.arxiv.org. Add this host to your network egress settings to allow access.

$ curl https://arxiv.org/ -> 000 (CONNECT tunnel failed, response 403) $ curl https://export.arxiv.org/ -> 000 (CONNECT tunnel failed, response 403) ```

arxiv.org, export.arxiv.org, www.arxiv.org 모두 프록시 CONNECT 단계에서 차단된다. WebFetch 도구로도 동일하게 403이다. fetch.py의 버그가 아니며, 스크립트는 그대로 두면 된다.

직전 회차(2026-08-04)는 launchd로 로컬 맥에서 돌아 정상 동작했다. 그 뒤 9ab8645 chore(radar): switch daily run from launchd to cloud routine로 실행 위치를 클라우드로 옮겼는데, 새 환경의 egress 정책에 arXiv가 빠져 있어 첫 클라우드 회차부터 막혔다.

조치 필요

Claude Code 웹의 환경 설정 → 네트워크 egress 허용목록에 다음을 추가해야 한다.

  • export.arxiv.org — API 조회 (fetch.py)
  • arxiv.org — 채택 논문 PDF 다운로드 (https://arxiv.org/pdf/<ID>)

둘 다 필요하다. API만 열면 후보 수집은 되지만 3단계 PDF 저장에서 다시 막힌다.

seen.json을 갱신하지 않은 이유

의도적으로 last_run을 밀지 않았다. 2026-08-04T08:13:50+00:00에 그대로 둔다.

fetch.py의 filter_new()는 published <= last_run인 항목을 버린다. 여기서 last_run을 오늘로 당기면, 접근이 복구된 뒤 08-04 ~ 08-06 사이에 게재된 논문이 조회 결과에서 통째로 제외되어 영구히 누락된다. 수집이 성공해서 신규가 0건인 회차와 달리, 이번엔 그 구간을 아직 한 번도 못 봤으므로 커서를 전진시키면 안 된다.

허용목록 수정 후 다음 실행이 08-04 이후 구간을 그대로 이어서 조회한다. 수동으로 즉시 따라잡으려면:

``bash python3 "0-papers/.radar/fetch.py" --since 2026-08-04T08:13:50+00:00 ``
